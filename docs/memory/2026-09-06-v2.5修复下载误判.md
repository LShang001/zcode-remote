# 2026-09-06 v2.5:修复更新下载被误判卡住(每个源下载一半即换源)

> 用户真机报告 v2.4 更新时"每个下载源都下载一半就退出,最终失败"。versionCode 16 / v2.5,已发 Release。

## 根因(两层叠加)

1. **stall 判定漏了 STATUS_PENDING(主因,已修)**:`progressPoller` 的卡住判定只在 RUNNING 且字节 20 秒不增长时触发,但 DownloadManager **排队**(等网络/代理解析)时状态是 PENDING、字节必然 0、旧代码不刷新 `dlLastProgressAt`——等待时长全部累进判定,转 RUNNING 后第一次轮询就"已等待>20s"被误杀。PAUSED 有同样问题但 v2.3 已修,PENDING 漏了。
2. **20s 阈值太激进(已修)**:gh-proxy 类代理是流式中转,回源卡顿/弱网抖动 20s+ 常见;匀速下载时 20 秒恰好是"一半进度"——与用户"每个都下载一半就退出"的描述精确吻合(20 秒定时器特征)。

修复:PENDING 与 PAUSED 一样持续刷新计时戳;阈值 20s → 60s(`DL_STALL_TIMEOUT_MS`)。

## 模拟器 A/B 验证的方法与发现

**方法**:要验证"新代码下载同一个真包",但装了 v2.5 就不会弹更新——`sed` 临时把 build.gradle 改成 `versionName "2.4"/versionCode 15` 构建一个**代码含修复的伪装 v2.4**,装进模拟器后检查更新会发现真 v2.5(2.5>2.4)并用新逻辑下载同一个包。测完立即恢复版本号重建正式包,**不提交、不覆盖 ZCodeRemote.apk 时机要掐准**。

**发现**:模拟器(宿主机代理 fake-ip 环境)下两个版本都在源 4(gh.llkk.cc)的 **20% ≈ 67KB 处断流**——67KB 恰是代理缓冲区典型大小,新代码 5 秒内就报失败,说明是 DownloadManager `STATUS_FAILED` 真断流而非 stall 误杀(60s 阈值 5 秒内不可能触发)。**结论:代理网络环境下镜像真断流,换源是正确行为,端到端下载验证只能靠真机**;模拟器只能验证"检查更新→弹窗→发起下载→状态机轮换"这段。

## 相关耐久知识(已同步 AGENTS.md)

- DownloadManager 的 PENDING/PAUSED 都是"字节必然不动的调度态",stall 判定必须对两者持续刷新计时戳,否则等待时长被算进卡住判定。
- 判定"误杀 vs 真断流"看失败耗时:远小于 stall 阈值就失败 = STATUS_FAILED 真断流;固定进度点失败且该点≈缓冲区大小 = 代理流断。
